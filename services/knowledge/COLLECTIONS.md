# OPCB 综合知识库：收藏与产物候选

用户方向：在现有 OPCB 知识库统一承接收藏、图片等资料，按类型细分。来源：buzz://message?channel=2dbc1afc-1556-4d45-8a35-c6c34e91a651&id=04de89bce3523a351762c4ee45b4eaf4e5177c0c7b7160250bf871b9afe68dda。

## 模型与实际范围

- 业务分类沿用现有库/子库；文件类型独立为 document / image / video / audio / link；项目等信息作为标签与成果名。
- 聊天保留执行过程、V1/V2/V3 与认可标记。入库保存选中的具体版本、来源频道和消息、原始 URL、源版本号及实际入库操作者。收藏与入库各自显示，不自动上传全部历史收藏。
- 默认保存到所属个人隔离空间。当前库授权关闭、个人停用、设备撤销会拒绝后续读取与上传；Agent 使用所属人证明，但不继承管理权限，也不能读取其他人的私人入库内容。
- 图片等附件保存原文件，SHA256 校验后回读；普通网页明确保存链接引用，不冒充网页全文。当前文件最多 32 MiB、每个人文件声明容量 256 MiB、最多 10,000 条记录，128 KiB 分块。检索为标题/标签/来源元数据关键词，不含自动 OCR 或语义检索。
- 入库文件保存在服务端，授权设备可以读取；界面的爱心和版本归组仍为本机 preferences。未承诺全员共享、跨设备自动同步所有标记或自动合并文件内容。

## 身份、协议与失败状态

继续使用现有 challenge/bind、P-256 非导出私钥及每请求 nonce/时间签名。新增 `collect` 角色绑定，原有 read 设备只能 list/get，不能 begin/append/commit。贡献身份与读取身份隔离；Agent 的贡献密钥按实际 Agent 公钥单列，服务端记录原生签发者。

`POST /collect` 接受严格 JSON 操作：

1. begin：元数据及大小、SHA256、MIME；同一所属人/来源去重，内容冲突返回 409。
2. append：按顺序写入固定最大 128 KiB 分块，相同分块重试幂等，错序、字节冲突和超额拒绝。
3. commit：核对完整大小及 SHA256 后才公开为 complete；不完整上传不进入列表。
4. get/list：每次核验所属人、库权限与停用状态；get 可以按 seq 读取原文件，list 可按类型/字面关键词筛选。
5. 客户端在 commit 后再次 get 并核对回执，才写入“已入库”标记。丢失确认可用相同来源和哈希继续读取/续传，不盲目创建第二份。权限变化时先恢复授权再核对，不声称未保存。

服务不会抓取提交 URL、访问客户端文件路径或接收 owner/管理员声明。存储目录由服务启动参数提供，数据库要求服务账号所有且 0600，父目录私有。资料内容只作数据，不执行 HTML、脚本或指令。

## 可审查的启用步骤

先在独立候选目录运行完整 `npm run ci`，保留现行服务、索引、policy.sqlite3、identities.sqlite3 与反代配置。服务包为 releases/OPCB_KNOWLEDGE_COLLECTIONS_RC7_SERVICE.zip；不包含运行配置、真实资料、设备密钥或授权库。

1. 由获准操作者将包放入独立版本目录，沿用已核实的现行 `--root`、`--policy-root`、`--community`、`--admin`、`--node` 参数，并将 `--verifier` 指向该目录的 dist/identity-auth.mjs。
2. 显式增加 `--collection-root <服务账号所有的私有数据目录>`。此开关创建收藏子库与 source 映射，写入配置审计，保留现有名称和授权；不新增人员授权。已存在的 collection 映射不同则拒绝，需明确迁移。
3. 现有 api/v2 代理仅增加固定 collect 路由（如果当前逐路径白名单），保留原路由与服务；验证配置后切换。匿名、读设备上传、他人私有 ID、停用及撤权必须拒绝。
4. 两个实际设备分别原生审核阅读插件与聊天插件，验证本人/Agent 入库、重试去重、图片哈希回读、类型检索及来源跳转。管理插件兼容构建单列，不强制扩大权限。
5. 回退时恢复上一服务/验签 bundle 和本次路由改动，停用 collect 路由；保留新增入库数据库及现有索引、策略、绑定，不删除资料、不覆盖并行配置。
